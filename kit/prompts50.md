# 🎁 Claude Codeプロンプト集50選

Claude Codeに「そのまま話しかけるだけ」で使える実用プロンプトを50個、5つの場面別にまとめました。ブレスト・開発・環境構築・自動化・ドキュメント作成まで、日々の作業でよくある依頼をそのまま文章化しています。

**使い方**: そのままコピーしてClaude Codeのプロンプトに貼り付けるだけで使えます。〇〇の部分は自分の状況に合わせて書き換えてください。

---

## 1. ブレインストーミング・要件定義系

### 1. 漠然としたアイデアを言葉にする
頭の中にあるだけのアイデアを、質問を重ねながら要件に落とし込みたいときに使う。
```text
〇〇というアイデアがあるのですが、まだ漠然としていて自分でもうまく言葉にできていません。いきなり実装や提案には進まず、まず「誰のためのものか」「何に困っているのか」「なぜ今やりたいのか」を中心に質問してください。ある程度整理できたら、最後に箇条書きの要件リストにまとめてください。
```

### 2. 新機能追加前の要件洗い出し
機能を思いつきで作り始める前に、抜け漏れなく要件を出してもらう。
```text
既存の〇〇に「△△機能」を追加したいと考えています。実装を始める前に、必要な入力・出力・想定するユーザー操作・エラー時の挙動を洗い出してください。私が答えられる範囲で質問してもらって構わないので、対話形式で要件を固めていきましょう。
```

### 3. 複数の設計案を比較検討する
一つの正解に飛びつく前に、選択肢を並べて長所短所を見たいときに使う。
```text
〇〇を実現する方法として、思いつく設計アプローチを2〜3案出してください。それぞれのメリット・デメリット・実装コスト・将来の変更しやすさを表にまとめてもらえると比較しやすいです。おすすめがあれば理由付きで教えてください。
```

### 4. 既存アプリへの機能追加の影響範囲を洗い出す
コードを触る前に、どこまで波及するかを事前に把握したいときに使う。
```text
このプロジェクトに〇〇という変更を加えると、どのファイルやどの機能に影響が出そうか調べてください。まだ実装はせず、影響範囲の一覧と、変更する際に注意すべき点だけをまとめて報告してください。
```

### 5. ユーザーストーリーとユースケースを整理する
機能仕様を書く前段階として、利用者視点のシナリオを固めたいときに使う。
```text
〇〇というサービス（または機能）について、想定される利用者像を2〜3パターン挙げて、それぞれがどんな場面でどう使うかというユーザーストーリーを書いてください。抜けていそうな利用シーンがあれば指摘もお願いします。
```

### 6. 技術選定・アーキテクチャの相談
ライブラリや構成を決める前に、判断材料をもらいたいときに使う。
```text
〇〇を作るにあたって、△△と□□のどちらの技術・ライブラリを選ぶべきか迷っています。今回の要件（規模・想定利用者数・保守のしやすさ）を踏まえて、それぞれの向き不向きを整理し、判断の材料をください。まだ結論を急がず、私の意見も聞きながら一緒に決めたいです。
```

### 7. 個人開発・小規模プロジェクトのMVPスコープを決める
やりたいことが多すぎて手が止まっているときに、最初の一歩を絞り込む。
```text
〇〇を個人で作りたいのですが、やりたい機能が多すぎて何から手をつけるべきか決まっていません。最初のバージョン（最小限で動くもの）に入れるべき機能と、後回しにしてよい機能を分けて提案してください。
```

### 8. データの持ち方（テーブル設計）を相談する
コードを書き始める前に、データ構造の妥当性を確認したいときに使う。
```text
〇〇というアプリで扱うデータ（△△、□□など）を、どのようなテーブル構成・データ構造で持つのが適切か相談したいです。いくつか案を出したうえで、それぞれの想定されるメリットと将来の変更のしやすさを説明してください。
```

### 9. 画面構成・UIのたたき台を相談する
実装前に画面の骨格を言葉で固めておきたいときに使う。
```text
〇〇というツールの画面構成を考えています。主要な画面が何枚必要で、それぞれにどんな要素を置くべきか、たたき台となる構成案を出してください。まだデザインは不要なので、要素の一覧と画面同士のつながりが分かる形でお願いします。
```

### 10. 小規模チームでの開発ルール・進め方を決める
複数人での作業を始める前に、進め方の土台を一緒に決めたいときに使う。
```text
2〜3人でこのプロジェクトを進めることになりました。ブランチの運用ルール、コミットメッセージの書き方、レビューの流れについて、このチームの規模に合ったシンプルなルール案を提案してください。決定事項はあとで参照できるようにファイルにまとめてください。
```

## 2. 開発・デバッグ・レビュー系

### 11. 原因不明のバグを一緒に調査する
エラーの原因が分からず手が止まっているときに、順を追って切り分けてもらう。
```text
〇〇を実行すると△△というエラーが出ますが、原因が分かっていません。憶測で直接コードを書き換えるのではなく、まずログや関連コードを確認して原因の仮説を立て、仮説を検証してから修正案を提示してください。
```

### 12. 読みにくいコードのリファクタを依頼する
動いてはいるが読みにくいコードを整理してもらいたいときに使う。
```text
〇〇のファイルにあるコードが読みにくく、変更しづらくなっています。挙動は変えずに、命名や関数の分割、重複の整理を目的にリファクタしてください。変更前後で動作が変わっていないことを確認できる方法も教えてください。
```

### 13. 既存機能にテストを追加してもらう
テストがない状態の機能に、安心して変更できるようにテストを足したいときに使う。
```text
〇〇の機能にまだテストがありません。主要な正常系と、想定される異常系（不正な入力や境界値など）をカバーするテストを追加してください。実装より先にテストの内容を私に見せて、それから書き進めてください。
```

### 14. PR（プルリクエスト）のレビューを依頼する
自分の変更をマージする前に、第三者視点でチェックしてもらいたいときに使う。
```text
このブランチの変更内容をレビューしてください。バグの可能性、命名や設計上の違和感、テストの不足、既存コードとの一貫性の観点で確認し、指摘事項を優先度付きでまとめてください。
```

### 15. 既存コードの説明を求める
自分が書いていない、または久しぶりに触るコードの理解を助けてもらいたいときに使う。
```text
〇〇のファイル（またはこの関数）が何をしているのか理解できていません。処理の流れを、前提知識がなくても分かるように順を追って説明してください。特に分かりにくい部分があれば図や具体例も使ってください。
```

### 16. 動作が遅い処理の原因調査
体感で遅いと感じる処理があるが、どこがボトルネックか分からないときに使う。
```text
〇〇の処理が遅く感じています。どこに時間がかかっているのか調査し、原因を特定してください。改善案がある場合は、実装コストと効果の見込みを添えて提案してください。
```

### 17. セキュリティ観点でコードを見てもらう
公開前に、基本的なセキュリティ上の見落としがないか確認したいときに使う。
```text
このプロジェクトを外部に公開する前に、入力値の扱い、認証・認可、秘密情報の管理まわりに問題がないかセキュリティ観点でレビューしてください。見つかった懸念点は、深刻度と対応の目安を添えて報告してください。
```

### 18. ライブラリのアップデートによる影響調査
依存ライブラリを更新したいが、壊れる箇所がないか不安なときに使う。
```text
〇〇というライブラリを最新バージョンに上げたいのですが、破壊的変更がこのプロジェクトのどこに影響しそうか調べてください。実際にアップデートする前に、影響箇所と対応が必要な作業の一覧を教えてください。
```

### 19. エラーログから原因を切り分けてもらう
大量のログの中から、問題の核心を見つけたいときに使う。
```text
このエラーログ（またはログファイルの場所）を確認して、今回の不具合に関係がありそうな行を絞り込んでください。無関係なノイズは除外したうえで、原因として考えられる箇所を根拠付きで説明してください。
```

### 20. 重複しているコードをまとめてもらう
似たような処理があちこちにあり、共通化したいときに使う。
```text
このプロジェクト内で似たような処理が複数箇所に散らばっていないか調べてください。共通化できそうな部分が見つかったら、既存の挙動を壊さない範囲で共通関数（またはモジュール）にまとめる提案をしてください。
```

## 3. スキル自作・環境構築系

### 21. 繰り返し作業を専用スキルにしてもらう
毎回同じ手順で頼んでいる作業を、自分専用のコマンドにしたいときに使う。
```text
私はいつも〇〇という作業を、△△→□□という手順で依頼しています。この手順をSKILL.mdとしてスキル化し、次からは短い指示だけで同じ品質の結果が得られるようにしてください。作成後は簡単な例で動作確認もお願いします。
```

### 22. プロジェクトのCLAUDE.mdを整備してもらう
このプロジェクト特有のルールや前提を、毎回説明しなくて済むようにしたいときに使う。
```text
このプロジェクトについて、今後の作業で毎回伝えるのが手間になっているルールや前提（ディレクトリ構成、コーディング規約、注意点など）をCLAUDE.mdとしてまとめてください。既存のCLAUDE.mdがあれば重複させず、不足している部分だけ追記してください。
```

### 23. 特定作業専門のサブエージェントを定義してもらう
特定の役割（レビュー専門、調査専門など）を切り出して任せたいときに使う。
```text
〇〇という作業だけを専門に担当するサブエージェントを定義してください。役割の範囲、使ってよいツール、報告してほしい形式を明確にしたうえで、実際に一度呼び出して動作を確認してください。
```

### 24. 大きな変更の前にまず計画を立ててもらう
いきなりコードを変更されると困る規模の作業のときに使う。
```text
〇〇を実装してほしいのですが、規模が大きいのでいきなりコードは変更しないでください。まず変更方針と作業手順を計画としてまとめて提示し、私が確認して承認してから実装に進んでください。
```

### 25. 既存スキルの改善を依頼する
すでにあるスキルの使い勝手が悪い、失敗しやすいと感じるときに使う。
```text
〇〇というスキルを使うと、いつも△△の部分でうまくいかないことが多いです。原因を確認したうえで、同じ失敗を繰り返さないようにスキルの手順や指示文を改善してください。修正後は同じ状況を想定して一度試してください。
```

### 26. 特定操作前に確認を挟むルールを設定してもらう
取り消しにくい操作の前に、必ず一度立ち止まってほしいときに使う。
```text
〇〇のような取り消しにくい操作（削除・上書き・外部への送信など）を行う前には、実行前に必ず内容を確認してから進めるように設定してください。設定後、実際にそのような操作が発生する場面で正しく確認が入るか一緒に確かめてください。
```

### 27. 開発環境のセットアップ手順を自動化してもらう
新しい環境やメンバーが加わったときに、毎回手作業でセットアップするのが手間なときに使う。
```text
このプロジェクトの開発環境を新しく用意する手順を洗い出し、できる範囲でスクリプトやコマンド一つで完了できるようにまとめてください。手動でしか対応できない手順が残る場合は、その理由と手順も明記してください。
```

### 28. プロジェクト構造をドキュメント化してもらう
プロジェクトの全体像が把握しづらくなってきたときに使う。
```text
このプロジェクトのディレクトリ構成と、それぞれの役割を把握したいです。主要なフォルダ・ファイルが何を担っているかを整理し、初めて見る人でも全体像がつかめるドキュメントとしてまとめてください。
```

### 29. よく使う指示をスラッシュコマンド化してもらう
毎回同じような長い指示を打ち込んでいるのを短縮したいときに使う。
```text
私は普段〇〇という指示を繰り返し使っています。これをスラッシュコマンドとして定義し、短いコマンド名で同じ内容の依頼ができるようにしてください。作成後、実際に一度呼び出して意図通りに動くか確認してください。
```

### 30. 自動実行してよい操作とNGな操作の線引きを相談する
どこまで自動で進めてよいか、自分なりの基準を決めたいときに使う。
```text
このプロジェクトで作業する際、どの操作までは確認なしで自動的に進めてよく、どこからは必ず私に確認を取ってほしいか、一緒に基準を整理したいです。ファイルの削除・外部送信・課金が発生する操作などを軸に、線引きの案を提案してください。
```

## 4. 自動化・外部連携系

### 31. MCP経由でSlackへの通知をお願いする
作業の区切りをSlackに知らせてほしいときに使う。
```text
このタスクが完了したら、Slackの〇〇チャンネルに完了報告を送ってください。内容は、何を行ったか、結果はどうだったか、次にやるべきことがあれば何かが分かる形で、太字などの装飾は使わずシンプルな文章にしてください。
```

### 32. MCP経由でNotionのタスク管理を操作してもらう
Notionのタスクデータベースの整理を手伝ってほしいときに使う。
```text
Notionの〇〇というデータベースを確認し、期限が過ぎているタスクと、担当者が未設定のタスクを一覧にしてください。一覧を出すだけで、実際の変更（削除やステータス更新）は私が確認してから行ってください。
```

### 33. MCP経由でGoogleカレンダーの予定を確認・整理してもらう
今週の予定を整理して見通しを立てたいときに使う。
```text
今週のGoogleカレンダーの予定を確認し、空いている時間帯と、詰まりすぎている日を教えてください。新しい予定を追加する提案がある場合も、実際の登録は行わず提案だけにとどめてください。
```

### 34. 毎朝の定型チェックを自動実行するルーティンを組んでもらう
毎日繰り返す確認作業を自動化したいときに使う。
```text
毎朝〇〇の状態（例:未読の問い合わせ件数、サーバーのエラーログ、昨日の数値実績など）を確認し、簡単な要約を私に届けてほしいです。これを毎日決まった時間に自動で実行される仕組みとして設定してください。
```

### 35. どこまで自動化してよいか方針を相談する
自動化の範囲を広げる前に、リスクとのバランスを一緒に考えたいときに使う。
```text
〇〇という繰り返し作業を自動化したいのですが、どこまで人の確認なしで自動実行してよいか判断がつきません。作業内容ごとにリスクの大小を整理し、自動化してよい範囲と、必ず確認を挟むべき範囲を提案してください。
```

### 36. 複数エージェントに役割分担させて大きめの作業を進めてもらう
一人でこなすには重い作業を、役割分担して並行で進めたいときに使う。
```text
〇〇という作業をいくつかの役割（調査担当、実装担当、レビュー担当など）に分けて、複数のエージェントで並行して進めてください。それぞれの担当範囲を明確にしたうえで進行し、最後に全体の結果をまとめて報告してください。
```

### 37. 重要な変更をクラウドで深くレビューしてもらう
リリース前など、いつもより踏み込んだレビューを受けたいときに使う。
```text
この変更はリリース前の重要なものなので、通常より踏み込んだレビューをクラウド上で行ってください。見つかった問題は深刻度別に整理し、対応が必要なものと様子見でよいものを分けて報告してください。
```

### 38. 外出先からスマホで作業の続きを進める
外にいる間も、進行中の作業を確認・指示したいときに使う。
```text
今進めてもらっている〇〇の作業について、外出中でもスマホから進捗確認と簡単な指示出しができるようにしたいです。現状どこまで進んでいるかを共有できる状態にしておいてください。
```

### 39. 外部APIとの連携部分の動作確認をしてもらう
外部サービスと繋いだ処理が、想定通り動くか確かめたいときに使う。
```text
〇〇の外部API連携部分について、想定しているリクエストとレスポンスの流れが正しく動くか確認してください。実際に外部へ送信・課金・投稿が発生する操作は、事前に必ず私に確認してから実行してください。
```

### 40. 週次で自動生成してほしいレポートの仕組みを作る
毎週手作業でまとめているレポートを自動化したいときに使う。
```text
毎週〇〇のデータをもとに作っているレポートを、決まった曜日・時間に自動で下書きが作られる仕組みにしたいです。集計する項目とレポートの形式を一緒に整理したうえで、その仕組みを設定してください。
```

## 5. ドキュメント・コミュニケーション系

### 41. 変更内容からコミットメッセージを作ってもらう
何を直したかは分かっているが、メッセージにまとめるのが手間なときに使う。
```text
今回の変更内容を確認し、変更の目的が伝わるコミットメッセージ案を作成してください。何を変えたかだけでなく、なぜその変更が必要だったのかが分かる一文を添えてください。
```

### 42. プロジェクトのREADMEを作ってもらう
初めて見る人にプロジェクトの概要が伝わるようにしたいときに使う。
```text
このプロジェクトのREADMEを作成してください。プロジェクトの目的、セットアップ手順、基本的な使い方が、初めて見る人にも伝わる構成でお願いします。すでにREADMEがある場合は上書きせず、不足している部分を補ってください。
```

### 43. 今日の作業内容を進捗報告としてまとめてもらう
一日の作業を振り返り、共有用の報告文にまとめたいときに使う。
```text
今日のセッションで行った作業内容を振り返り、進捗報告としてまとめてください。完了したこと、まだ残っていること、次回着手予定のことに分けて、簡潔な文章でお願いします。
```

### 44. 非エンジニアの上司・同僚向けに変更点を説明してもらう
技術的な変更を、専門用語を使わずに説明してほしいときに使う。
```text
今回行った〇〇の変更内容を、エンジニアではない人にも伝わるように説明してください。専門用語はできるだけ避け、日常的な言葉や身近な例えを使って、何がどう良くなったのかが分かる文章にしてください。
```

### 45. 変更履歴(CHANGELOG)を整備してもらう
過去の変更を振り返れる記録として残しておきたいときに使う。
```text
このプロジェクトのこれまでのコミット履歴を確認し、利用者にとって意味のある変更（機能追加・不具合修正・仕様変更など）を中心にCHANGELOGとして整理してください。細かい内部的な修正は省略して構いません。
```

### 48. 技術的負債を非エンジニアにもわかる言葉で説明してもらう

```text
このプロジェクトに溜まっている技術的な課題（技術的負債）について、専門用語を使わずに、放置した場合のリスクと、対応した場合のメリットが伝わるように説明してください。読み手は技術に詳しくない人を想定してください。
```
